Qué podemos sacar de CopilotKit

CopilotKit no es una librería de chat: es una pila de tres capas (protocolo, SDKs y producto). Lo verdaderamente aprovechable para Codync está en el protocolo y en el renderizador declarativo, no en sus componentes de interfaz. Y hay un dato que cambia la estrategia: OpenBot es un producto construido sobre esta misma pila.

3. Aclaración necesaria: hay dos OpenBot

Corrección importante sobre la primera versión de este documento: CopilotKit/OpenBot no es el OpenBot que Codync está integrando. El nuestro es nightly-labs/openbot, un proyecto distinto que comparte el nombre. Lo que sí comparten es la categoría: un espacio de trabajo de agentes. CopilotKit construye el suyo sobre AG-UI y A2UI, y por eso sirve como implementación de referencia; no como código de origen.

Consecuencia práctica: el valor del protocolo no depende de esa coincidencia. AG-UI y A2UI valen por sí solos porque son estándares abiertos con SDKs en muchos lenguajes y clientes reales; la alineación con nightly-labs no entra en la decisión. Lo que sí se puede aprovechar del OpenBot de CopilotKit es el patrón: cómo una app de agentes usa eventos de estado, aprobaciones y UI generativa sobre el mismo stream.

Regla de puente de siempre: los nombres del protocolo se conservan (eventos, campos, semántica AG-UI/A2UI); lo único que cambia es la marca visible en Codync. Y de nightly-labs/openbot se sigue copiando código como hasta ahora: nada de este documento lo sustituye.

4. Lo que se puede sacar, ficha por ficha

C1Codync como servidor AG-UI (SSE)

Qué
Exponer cada bot del host como endpoint AG-UI: POST /agui/{bot} que recibe un run input y responde un stream SSE de eventos estándar (run started, texto delta, tool call, state delta, run finished, run error, aprobación pendiente).
Por qué
Convierte a Codync en backend para cualquier frontend AG-UI: CopilotKit React, Angular, Vue, React Native, Slack y Teams. Los bots de Codync dejan de estar encerrados en sus propias apps.
Cómo
El host ya emite eventos internos por WebSocket; se añade un traductor host/src/agui/ (serializador de eventos + SSE + mapeo de errores). No hace falta el SDK: el protocolo son ~16 tipos de evento y los publica el propio repo. El SDK Rust de la comunidad (ag-ui-core, ag-ui-client) está en estado embrionario; se usa como referencia, no como dependencia fija.
Terminado cuando
Un ejemplo oficial de CopilotKit apunta a localhost del host, elige un bot y ve texto en streaming, una tool y una aprobación funcionando sin cambios en el host más allá del endpoint.

C2Codync como cliente AG-UI (agentes externos como proveedores)

Qué
Lo inverso: en Ajustes de proveedores, "Agente AG-UI" con URL; el host consume el stream de ese agente como si fuera un CLI más. Cubre LangGraph, CrewAI, Mastra, ADK, PydanticAI, Claude Agent SDK y los agentes de OpenBot.
Por qué
Un solo adaptador abre decenas de frameworks sin escribir un proveedor por cada uno.
Cómo
Cliente SSE + parser de eventos AG-UI en host/src/agent/providers/agui.rs; mapear tool calls del agente remoto a las tools y aprobaciones locales; estado compartido entra al hilo como "estado del agente".
Terminado cuando
Un bot con proveedor AG-UI apunta al Dojo de AG-UI y responde en Codync con streaming y aprobaciones.

C3UI generativa declarativa con A2UI en el chat

Qué
El agente manda UI como datos (formularios, tarjetas, tablas, gráficos) y Codync la renderiza con sus componentes nativos. No hay HTML ni código ejecutable del modelo: el catálogo define qué puede pedir.
Por qué
Encaja exactamente con la regla de la casa (el host manda, los clientes dibujan) y con la promesa de estados ricos: aprobaciones con campos, formularios de claves, tarjetas de plan. Los renderizadores existen para React y SwiftUI; el de Android habría que escribirlo (o pasar por el web renderer en el WebView existente).
Cómo
Catálogo base propio con los componentes de Codync (aprobación, formulario, tabla, gráfico, imagen, selección) validado por esquema; el host emite mensajes A2UI por el mismo SSE del C1; escritorio usa @a2ui/react mapeado a componentes propios; iOS usa A2UISwiftUI; Android, en fase 2, con su adaptador Compose o con el renderer web ya existente.
Terminado cuando
Un bot pide una clave con un formulario A2UI nativo en escritorio y en iPhone, y la aprobación se manda al host con los campos rellenados.

C4Estado compartido y herramientas de frontend

Qué
El patrón useAgent + setState: el agente y la UI leen y escriben un mismo estado, y el agente llama funciones de la app (no del host) para actuar sobre lo que el usuario ve.
Por qué
El lienzo, las fichas de rutina y el plan son candidatos naturales: el agente puede abrir una ficha, cambiar un filtro o preparar una rutina mientras el usuario mira. Hoy eso se hace por eventos sueltos.
Cómo
Definir el esquema de estado por vista en el host (fuente de verdad) y un canal de "acciones de vista" con nombre y validación; la UI las ejecuta y devuelve resultado. No se copia el hook de React: se copia la semántica del mensaje.
Terminado cuando
El usuario dice "ponme una rutina el lunes a las 8" y la ficha aparece y queda configurada sin que el agente toque la base directamente.

C5Channels: un mensaje, Block Kit y Adaptive Cards

Qué
Escribir la tarjeta una vez (JSX) y que se renderice como Block Kit en Slack, Adaptive Cards en Teams, componentes en Discord y texto con formato en WhatsApp.
Por qué
Codync ya tiene canales en Slack, Discord, Telegram y WhatsApp. Hoy cada salida se formatea a mano; este modelo unifica y mejora la calidad de las tarjetas de aprobación y de los informes de rutina.
Cómo
El paquete es TypeScript, así que no entra al host: se porta el modelo al formateador de canales del host (host/src/channels/) como serializadores por plataforma, manteniendo el formato de origen (Block Kit y Adaptive Cards) para no re-autorizar nada.
Terminado cuando
Una aprobación de rutina con botones se ve como Block Kit en Slack y como Adaptive Card en Teams, y en WhatsApp como lista de opciones.

C6WebMCP: exponer acciones de Codync al navegador

Qué
Declarar acciones de la app como herramientas de navegador para que un agente web (el navegador propio de Codync, o uno externo) las invoque.
Por qué
El navegador de los bots ya vive en la app: con WebMCP, el agente puede "pedir" acciones de la interfaz de forma estándar en vez de simular clics.
Cómo
Es una propuesta joven: se estudia y se implementa solo para las acciones internas del navegador embebido; no se envía nada a terceros.
Terminado cuando
El agente abre el panel de archivos de Codync desde el navegador integrado usando una acción declarada, sin clics simulados.

C7Inspector como herramienta de desarrollo

Qué
Superposición local que muestra hilos, agentes, eventos y estado mientras se construye la integración.
Por qué
Depurar el traductor AG-UI del host a ojo es caro; el Inspector hace visible cada evento y cada estado.
Cómo
Se usa solo en builds de desarrollo, apuntando al endpoint C1; no se empaqueta en producción. Es un paquete React: se monta en una ruta de desarrollo del renderer o en una ventana aparte.
Terminado cuando
Un evento mal formado se ve en el Inspector con su tipo, su secuencia y el error del cliente.

C8Voz del SDK

Qué
El paquete voice de CopilotKit: micrófono, dictado y conversación sobre el mismo stream AG-UI.
Por qué
Codync ya tiene voz propia; aquí lo aprovechable es el patrón de eventos de voz dentro del protocolo (audio como parte del stream), no el componente.
Cómo
Se toma como referencia para que un bot servido por C1 pueda ser hablado y dictado desde un cliente AG-UI externo.
Terminado cuando
Un cliente de ejemplo habla con un bot de Codync por AG-UI, con transcripción en el hilo.

C9aimock: pruebas de agentes sin claves reales

Qué
Un servidor de mocks para todo lo que habla una app de agentes: APIs de LLM, MCP, A2A, AG-UI, bases vectoriales y búsqueda. Un paquete, un puerto, sin dependencias.
Por qué
Hoy cada prueba de extremo a extremo de bots depende de una cuenta real o de un servidor falso casero. Con aimock se prueba el bucle completo, incluidas tools, streaming y aprobaciones, sin gastar cuota ni tocar la red.
Cómo
Se usa como binario/motor del runner de pruebas (Node ya está empaquetado para n8n): un mundo falso con respuestas grabadas y fallos programados; las pruebas del host apuntan ahí.
Terminado cuando
La suite de integración del host corre sin ninguna clave real y cubre un turno con tool, un error de proveedor y una aprobación.

C10matterbridge: el mapa de plataformas de chat

Qué
Puente con API REST entre más de veinte redes: Matrix, IRC, XMPP, Zulip, Rocket.Chat, Teams, Slack, Discord, Telegram, WhatsApp, Mumble y más.
Por qué
Codync tiene cinco canales; este repo demuestra los contratos de todos los demás. Sirve como mapa para decidir el siguiente canal sin reescribir conectores desde cero.
Cómo
No se mete como proceso: se lee su capa de adaptadores por plataforma y se portan al host solo las que se pidan (Matrix y Teams primero, por peso de uso).
Terminado cuando
Un canal nuevo de la lista se conecta desde Extensiones › Apps con su propia sesión y entrega mensajes con adjuntos.

C11OpenDuet: proactividad que no interrumpe

Qué
Plantilla de agente proactivo que trabaja por su cuenta y "te mantiene en el bucle": decide cuándo avisar, cuándo preguntar y cuándo seguir.
Por qué
Codync ya tiene check-ins proactivos y decisiones pendientes; este repo aporta el criterio de cuándo molestar y cómo agrupar avisos, que es justo lo que falta para que los check-ins no cansen.
Cómo
Se copia el patrón (no la app): política de interrupción, agrupación de avisos por hilo y estado "esperando al usuario".
Terminado cuando
Un bot proactivo agrupa tres hallazgos en un solo aviso y no vuelve a interrumpir hasta que haya respuesta o pase el plazo.

C12OpenDots: llamadas de voz y Slack en el mismo hilo

Qué
Coworkers siempre activos que pasan de texto a llamada y a Slack conservando el hilo.
Por qué
Codync ya tiene voz y canales; lo que no tiene es continuidad de conversación entre una llamada y el chat. Este repo enseña el modelo de sesión único entre superficies.
Cómo
Se adopta el concepto: el hilo es uno y las superficies (texto, voz, Slack) son vistas del mismo run; se implementa con el bus de eventos existente.
Terminado cuando
Una llamada de voz y el chat del mismo bot comparten contexto y la transcripción aparece en el hilo.

C13open-multi-agent-canvas y excalidraw-studio: patrones de lienzo

Qué
Un canvas donde varios agentes comparten una conversación y se añaden servidores MCP; y un estudio que genera, edita y exporta diagramas Excalidraw desde el chat con streaming.
Por qué
El lienzo de Codync ya tiene fichas y rutinas. Estos dos repos muestran el paso siguiente: varios agentes sobre el mismo tablero y objetos editables que el agente produce (diagramas), no solo tarjetas.
Cómo
El de Excalidraw se trae casi directo: es la respuesta a la conversación anterior sobre "un Figma ligero" — pizarra editable, sin servidores, con el archivo guardado como documento de Codync. El multiagente se toma como patrón de estado compartido sobre C4.
Terminado cuando
El bot crea un diagrama Excalidraw que se puede editar y guardar, y dos agentes colaboran en la misma ficha del lienzo.

5. Lo que no se trae, y por qué

  • Los componentes de chat de CopilotKit (sidebar, popup, chat UI): Codync tiene su propio sistema visual y sus reglas de controles. Traerlos sería un fork de interfaz que además choca con la paridad iOS/Android.
  • El runtime de CopilotKit como pieza de servidor: el host ya es el runtime; meter un runtime TS obligaría a un sidecar Node y duplicaría la lógica que el host ya tiene.
  • Intelligence (memorias gestionadas, continual learning, analítica): capa comercial; además ya tenemos memorias, skills y analítica propias.
  • CopilotKit Cloud / Soar: fuera de alcance, producto de pago.
  • El SDK Rust como dependencia: está en estado embrionario (repo comunitario con TODO); el protocolo se implementa directo y se usa el SDK solo para contrastar.
  • El renderizador A2UI de Android: no existe todavía; se hace propio o se usa el web renderer en el WebView.

6. Orden y esfuerzo

  1. C1 servidor AG-UI (3-4 días): el que más abre y el que menos riesgo tiene.
  2. C2 cliente AG-UI (3-4 días): con C1 comparte el serializador y el parser.
  3. C9 aimock para pruebas (1-2 días): sin esto, cada ficha posterior se prueba a mano.
  4. C3 A2UI en escritorio y iOS (4-6 días): catálogo propio y dos renderizadores.
  5. C4 estado compartido y acciones de vista (3 días).
  6. C5 canales con serializadores por plataforma (2-3 días); C10 para el siguiente canal que se pida.
  7. C13 Excalidraw (2-3 días) cuando se retome el "Figma ligero".
  8. C11, C12, C6, C7 y C8 según necesidad (1-2 días cada uno, opcionales).

Total realista: dos semanas y media para C1, C2, C9 y C3, que es donde está el valor. Todo MIT o Apache 2.0: se copia, se porta y se adapta sin condiciones.

7. Riesgos que hay que vigilar

  • Versión del protocolo: AG-UI va por 1.0 y A2UI también; fijar versión en el handshake y no perseguir la última sin plan.
  • Doble camino de eventos: el host ya tiene su WebSocket; el traductor AG-UI debe ser una vista del mismo bus, no un segundo mecanismo con estado propio.
  • Duplicación: no construir un proveedor AG-UI si ACP ya cubre el caso; decidir por uso real (ACP para agentes locales de terminal; AG-UI para agentes con interfaz y estado).
  • Android: sin renderizador A2UI nativo, no prometer paridad hasta tener el adaptador Compose o la ruta WebView probada.
  • Seguridad: A2UI valida contra catálogo y prohíbe código del modelo; nunca renderizar HTML generado. Esa es justo la razón para elegirlo.
